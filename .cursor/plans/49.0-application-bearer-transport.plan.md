## Scope

### In scope

- Default application-token transport: `Authorization: Bearer <miso-client-token>`.
- Optional legacy mode that still sets `x-client-token` on the shared httpx client / per-request headers.
- Dual-header safety: one application transport per request by default.
- Updates to `miso_client/utils/internal_http_client.py`, token manager, `auth_api.py`, Auth service, error handler auth-method labels.
- Tests (`tests/unit`, `tests/integration`, `test_integration.py` client-token cases) and docs.
- Consumer handoff for Dataplane (`getMisoHttpClient` / CIP interactions noted in 510).

### Out of scope

- Controller YAML/routes/OpenAPI (205).
- Dataplane call-site refactors beyond what a version bump + default change requires (separate Dataplane work after 510).
- Changing user/OAuth Bearer behavior.
- Inventing permissions client-side (permissions remain signed claims from controller).

## Rules and Standards

- Follow Python SDK project rules and quality gates (lint/test as defined in repo).
- Do not log token values.
- Keep public API aligned with TS SDK concepts (transport default + legacy opt-in).
- Extend existing `ClientTokenManager` / `InternalHttpClient` rather than adding a parallel HTTP stack.

## Before Development

1. Confirm 205 dual-transport acceptance of application Bearer.
2. Diff transport defaults with 65.0 so flag names/semantics match where practical.
3. Inventory emission sites: `internal_http_client.py` header assignment, `auth_api.validate_client_token(send_as_header=…)`, services that document x-client-token-only.
4. Note Dataplane CIP bearer-forward workaround (strips client-token) — Bearer-default should reduce that conflict; verify with 510 findings before cleanup.

## Architecture alignment

- Owner: Platform SDK (Python) — transport adapter for Miso application principals used by Dataplane.
- Controller classifies Bearer tokens by trusted claims (205); SDK does not infer principal type from headers alone.
- Parity with 65.0 is required so Node and Python apps migrate on the same contract.

## Code reuse scan

- Reuse `ClientTokenManager` fetch/cache; change attachment header only.
- Reuse `http_client_auth_helpers` Bearer helpers for user tokens; extend patterns for application tokens carefully (avoid overwriting user Bearer with app token on the same request).
- Reuse existing error taxonomy (`http_error_handler` auth method labels).

## Expected Automated Tests

- Default mode sets `Authorization: Bearer` for application token and does not set `x-client-token`.
- Legacy mode sets `x-client-token` when enabled.
- `validate_client_token` works when sending token as Bearer (and legacy header when requested).
- User Bearer / delegated auth paths unchanged.
- `[EDGE]` Missing/expired client token does not fall back to fabricating identity.
- Integration tests that assert `"x-client-token" in headers` updated for default Bearer.
