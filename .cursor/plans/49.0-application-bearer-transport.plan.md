One OAuth2 mechanism: trusted Keycloak client_credentials → Bearer token → verified principal
purpose → RBAC → resource/ABAC restriction. CI/CD, runtime and external-system identities are
separate accounts with separate authority, not separate token mechanisms. Runtime accounts are
per application/environment; system-only capabilities remain forbidden to humans and deployment
accounts even if they acquire the same permission string. No automatic application-auth bypass.
Internal runtime/external-system identities are hidden from normal account lists and never reveal
secrets; authorized rotation returns status only. No second docs-sync service account is added.

Inventories in 510/165 run first without product mutation; 205 freezes exact contract and minimum
consumer versions; code slices require current validation/approval. SDK implementation can then
proceed with controller compatibility; consumers cut over before legacy removal. A missing released
version is a prerequisite to resolve, not a version number to invent. Temporary legacy compatibility
is explicit per consumer, never a fallback after OAuth denial and never a permanent second model.

## Scope

### In scope

Standard OAuth2 client_credentials acquisition, token cache/renewal, trusted validation contract,
Bearer transport, runtime bootstrap and rotation integration, explicit user/deployment/runtime
selection, safe migration and released-package parity with SDK 65.0.

### Out of scope

Server policy issuance, permission invention, provisioning accounts in SDK code, embedding runtime
secrets in browsers, changing user login/session semantics, and a permanent custom app-token path.
This is not the former header-only switch of a Miso JWT into Authorization.

## Architecture alignment

The server-side SDK obtains an OAuth access token from the configured trusted Keycloak issuer,
then sends Bearer to the API. Miso owns purpose/binding/grants; resource servers enforce them.
A token decode for context/cache is not a successful verification. Use the agreed server verifier
or authenticated validation/introspection contract; do not trust a decoded permission/purpose field.
OAuth token replies keep standard protocol field names; adapt to the SDK's normal public naming.

## Code reuse scan

`internal_http_auth_strategy.py`, `miso_client/models/config.py` and existing auth/bootstrap helpers.
Retain current HTTP stack, error taxonomy, redaction and token cache architecture where suitable;
replace the custom grant URL/response assumptions. Inspect server-only and browser exports separately.
Existing rules describe x-client-token as current behavior; update those examples with rollout.

## Implementation plan

### 1. Freeze the shared SDK and server contract

Align with 205 and SDK 65.0: issuer discovery/token endpoint trust, client authentication method,
audiences/scopes, expiry/clock skew, response/error shape, purpose binding, authoritative validation,
credential reload, bootstrap owner context and legacy retirement. Preserve existing configuration
names where possible. Freeze public configuration changes and consumer versions before implementation;
never infer an arbitrary issuer endpoint from an unverified token or redirect.

Additional implementation best-practices to apply:

- Keep client secrets server-only and constrain token-request destinations before sending credentials.
- Share fixtures with the other SDK for protocol fields and security failures, not only happy headers.

### 2. Implement OAuth2 grant and expiry-aware caching

Use a dedicated non-intercepted request for client_credentials so token acquisition cannot recurse.
Parse access_token/token_type/expires_in and issuer expiry correctly; renew by obtaining a new token,
not by assuming a user refresh token exists. Serialize concurrent refreshes and bound retries.
Partition caches by issuer/client/audience/purpose and relevant binding. Reload credentials through
the established runtime configuration mechanism after managed rotation; never log the values.

Additional implementation best-practices to apply:

- Prevent token cache reuse across users, CI/CD accounts, runtime accounts or environments.
- Treat invalid_client/authorization denial as terminal until credentials/config change, not an
  invitation to try another identity.

### 3. Normalize Bearer transport and preserve user authority

Attach one chosen principal's Bearer token. Explicit human/session/delegation flows retain their
identity; do not overwrite user Authorization with a server token or append x-client-token to rescue
an invalid Bearer. Anonymous calls remain explicitly anonymous. Strip or reject conflicting headers
according to the frozen server contract. Never expose client secrets through browser APIs or URLs.

Additional implementation best-practices to apply:

- Make principal selection explicit before interceptor execution rather than header-priority guessing.
- Never broaden authority on retry of 401/403 or failed user-session recovery.

### 4. Adapt validation, bootstrap and managed rotation

Update existing auth/permission and bootstrap wrappers to the OAuth2 principal contract. Preserve
snapshot protocol/owner binding and configuration refresh independently from OAuth token renewal;
Miso bootstrap must not issue another proprietary application token as the permanent mechanism.
CI/CD cannot request runtime configuration; callers receive structured denials without fallback.
Managed rotation wrappers expose operation status only, and secret redaction covers all failures.

Additional implementation best-practices to apply:

- Preserve strict snapshot validation and report missing/denied configuration without fabricated defaults.
- Bound permission caches by authoritative revocation/expiry policy; failed validation grants nothing.

### 5. Release, verify consumers and remove legacy paths

Provide explicit compatibility only for named unmigrated consumers, not automatic protocol fallback.
Publish through the normal authorized release workflow after package tests; record actual minimum
versions and installed-artifact probes in 205. Test startup and rollback against compatible server
versions. After all consumers switch, remove custom token minting/header/query helpers and legacy
examples. Update current authentication rules/docs so users see one final OAuth2 model.

Additional implementation best-practices to apply:

- Test the packaged public entry points and avoid private imports or node_modules patches.
- Require consumer migration evidence before deleting compatibility, and never roll back RBAC isolation.

## Expected Automated Tests

- Grant: correct OAuth form/auth and standard response parsing, no API secret headers, no recursion;
  [EDGE] malformed token reply, untrusted endpoint/redirect, wrong token type and issuer outage.
- Cache: issuer/client/audience/purpose isolation, real expiry/skew, simultaneous refresh, rotated
  secret reload and bounded retries; disabled credentials do not trigger legacy fallback.
- Transport: one Bearer principal, user/session token retained, no conflicting client header,
  explicit anonymous requests and no credentials in browser bundles/URLs/logs/errors.
- Verification: forged decoded role/purpose is not accepted, wrong issuer/audience/expiry denied;
  server validation unavailable cannot yield permission success. Negative system-only API cases.
- Bootstrap/rotation: runtime owner snapshot compatible, CI/CD denial, missing required config
  explicit, status-only rotation, config refresh separated from token renewal.
- Package/compatibility: same shared fixtures as SDK 65.0, installed-package public API smoke,
  legacy mode explicit during migration, invalid Bearer never downgrades, legacy-off startup works.
