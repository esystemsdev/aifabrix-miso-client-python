# 52.0 Runtime client token lifecycle (Python SDK)

## Why

A consumer cannot cache around this correctly, and should not have to. The
runtime client is constructed by the SDK itself, so only the SDK can give it a
working cache.

```python
# miso_client/client.py:55 — at construction
self.redis = RedisService(config.redis)
```

```python
# miso_client/utils/bootstrap.py:52
async def init_secrets(*, http_client: Optional[httpx.AsyncClient] = None) -> SecretsRuntime:
```

`init_secrets()` takes no configuration, so `config.redis` is always `None` for
the runtime client it returns. `RedisService(None)` never connects, the cache is
inert, and `get_environment_token()` goes to the controller on every call. A
consumer that resolves a token per operation therefore mints per operation.

## Evidence (aifabrix-dataplane on dev03, 2026-09-28)

The Dataplane worker runs a sync sweep every few minutes. Each operation
resolved an application token:

```
/miso/api/v1/auth/token            120 x 401      6 x 201
/miso/api/security/parameters/decrypt   84 x 401

15:38  24 x 401     <- 11 mints inside one second
15:41  24 x 401
15:42  24 x 401
15:48  24 x 401
15:51  24 x 401
```

The controller refuses that rate. Every credential decryption that followed then
failed for want of a token, which is what the consumer first saw — so the
visible symptom (`parameters/decrypt` 401) was two steps away from the cause.

Corroborating observations from the consumer side:

- Zero `miso:*` keys in Redis, with `REDIS_URL` set and parseable — the runtime
  client never received the configuration the legacy client-credential path
  builds.
- `config.redis` is `None` on the runtime client while identical in every other
  respect to the legacy one (same `client_id`, `allowedOrigins`,
  `controllerPublicUrl`).
- An application token carries `exp - iat = 900` seconds, so a single token
  would have served an entire sweep.
- The same application authenticates normally elsewhere in the same window
  (`/v1/auth/bootstrap` 334 x 200, `/v1/logs` 1095 x 201), so this is rate and
  lifecycle, not identity or authorization.
- Strongest single indicator: immediately after a restart, before any sync sweep
  begins, `/api/v1/auth/token` returns **6 x 201 and zero 401s** for the same
  credentials. Refusals start only once the sweep drives the rate up. The
  credentials are good; the request rate is not.

## Scope

### In scope

- Holding a valid application token inside the client until shortly before
  expiry, without requiring any external cache.
- Allowing `init_secrets()` to receive cache/Redis configuration for consumers
  that want a shared cache across processes.
- Single-flight behaviour so concurrent callers cause one mint.
- Explicit semantics for expiry margin, unreadable tokens, failed mints and
  client-id isolation.

### Out of scope

- Any consumer-side cache. A workaround was written in `aifabrix-dataplane`
  (`ControllerApiClient.get_client_token`) and deliberately reverted: the
  lifecycle belongs here, and two caches would drift.
- Controller-side rate limiting or the refusal policy on `/api/v1/auth/token`.
- The transport split in plan 49.0, which is orthogonal.

## Acceptance

- Repeated `get_environment_token()` on a runtime client issues **one**
  controller request while the held token remains valid.
- A token within the refresh margin of `exp` is replaced, not served.
- Concurrent callers produce one mint, not one per caller.
- A token minted for one client id is never served to another.
- A failed mint is not held; an unreadable token is held only briefly, then
  retried.
- A consumer performing per-operation work over a 15-minute window makes ~1
  token request, not hundreds.
