## Scope and exclusions

In scope: remaining Python SDK objectives already in 607.0; minimal compatibility
fixes, reproducible owned environments, baseline adoption and existing workflow
updates necessary to deliver them.

Out of scope:

- Dataplane application dependencies, Docker images, API/health, Celery, NLP and
  inline execution: a library matrix cannot certify application behavior.
- Raising the Python floor, free-threaded Python, replacing pytest, changing the
  package backend or adopting another environment manager: none is required for
  the selected runtime upgrade. Revisit separately if a concrete blocker appears.
- Removing setup.py or redesigning all metadata ownership: reconcile effective
  package metadata within the existing structure; the upgrade does not require
  a packaging architecture migration.
- Unrelated authentication/API changes, new SDK features or broad dependency
  majors: retain public behavior; only evidenced compatibility fixes belong here.
- Publishing any new version, triggering releases or executing release commands:
  the user performs publication separately after this plan is complete.
- New release orchestration, mandatory new version,
  synchronized multi-repository releases or cloud mutations.

## Implementation tasks

### 1. Preserve and prove supported Python behavior

Retain >=3.11 and required 3.11–3.14 jobs. Keep static-analysis targets at 3.11;
`.python-version` selects current development Python without overriding explicit
matrix choices. Reuse `test_signal_handler` and
`test_signal_handler_without_running_loop` in `tests/unit/test_audit_log_queue.py`.
Inspect existing async lifecycle/HTTP, auth/error, Redis fallback, audit masking
and encryption tests before adding focused compatibility regressions.

Compare actual wheel METADATA with pyproject/setup support, version, dependencies
and intended extras. Correct drift, including basedpyright in developer setup,
without accidentally removing Flask/FastAPI extras or freezing consumer dependencies.
Preserve version mirrors; no bump merely for extracting this plan.

### 2. Lock owned environments and retain venv workflows

Use pip-tools to generate hashed third-party runtime/test/development/build
environments from reviewed inputs. Keep package dependency ranges in metadata;
include all tools actually used by Make/CI: pytest plugins, black/isort, ruff,
basedpyright, mypy, build, twine, setuptools/wheel and controlled bootstrap/generator
requirements. Constraints alone do not install runtime dependencies.

Prefer one compatible marker-aware resolved set where it serves all supported
interpreters. If resolution/platform differences require separate locks, use only
the necessary explicit environment variants with deterministic generation commands.
Pin generator/interpreter assumptions and check regeneration in CI without an
implicit upgrade mode. Install third-party dependencies with `--require-hashes`;
wrong/missing hashes fail. Do not add a network-dependent offline validation gate.

Install editable local SDK source separately without re-resolving dependencies.
Control PEP 517 build dependencies explicitly; hashing an sdist does not control
its build-isolation downloads. Use the existing backend with controlled build
requirements and an appropriate no-isolation invocation when needed. Verify
consumer sdist installation still works normally without repository Node tooling.

Extend existing Make setup rather than inventing another installer. Retain `venv`;
allow explicit interpreter selection and verify the environment interpreter before
reuse. Safely recreate only the managed incompatible environment, preserving .env
and unrelated files. Use runtime/lock identity for cache invalidation; failed
installation must not leave success state. Preserve editable `install`/`install-dev`
interfaces while routing owned development setup through controlled dependencies.

### 3. Supply SDK profile cases to the shared checker contribution

Give Dataplane positive/negative fixtures for `.python-version`, requires-python,
static setup.py mirrors, classifiers/static-analysis floor, workflow matrix and
SDK Node/tooling declarations. Distinguish package floor/current/next intentionally.
Missing applicable declarations fail; absence of an application Dockerfile must pass.

Dataplane implements Python support in
`aifabrix-miso/scripts/platform-baseline-check.mjs`; Miso reviews and accepts common
behavior with cross-profile fixtures. Use its reviewed exact TOML parser and shared
YAML dependency policy. Never execute setup.py to inspect metadata. Shared defects
are corrected canonically before copies are synchronized.

### 4. Adopt baseline through existing local gates

Copy the accepted baseline and checker identically into this repository, recording
canonical revision. Add minimal private root package.json, exact packageManager,
Node declaration, pnpm lock and development-only parser dependencies. Apply inherited
phase-aware build-script/release-age policy through compatible pnpm configuration;
future shared-library targets must not block the runtime phase.

Provide `make platform-baseline-check` and the pnpm alias for the same shared script.
Integrate with validate-silent, the non-silent path, CI and existing release callers
so normal validation cannot bypass it. Preserve format → lint → basedpyright →
type-check → test, failure propagation and `.temp/validation/` diagnostics.
Development setup explicitly provisions tools and performs frozen installation;
direct validation with missing tools fails with an actionable message and never
silently downloads tools or skips the check. Sibling parity is explicit; missing
Miso checkout is reported as parity unavailable, not a successful match.

Node/pnpm/parser tools are not Python runtime dependencies. Package installation,
import and use must succeed without Node. Do not add an application Dockerfile just
to satisfy a checker profile.

### 5. CI and distribution proof

Preserve Test workflow branch/PR coverage, bounded tests, type checks and CodeQL
workflow/release evidence. Keep supported Python jobs required. Add reported
non-blocking 3.15 readiness using the committed dependency set, not re-resolution
to hide incompatibilities. The inherited two-week green-readiness condition applies
to that reproducible set and dependency support; it does not authorize promotion.
Do not multiply the Python matrix by unrelated Node runtime jobs.

Provision Node separately for checker execution. Cache by actual interpreter and
lock/config identity; setup must not replace a selected floor/next interpreter.
Move publish.yml build/validation interpreter to proven current Python and use
controlled tooling without weakening immutable-tag/version/existing-artifact checks.
Retain token authentication and existing publish triggers. Add inherited Dependabot
pip/actions/tooling update coverage with grouped minor/patch and separate majors;
regenerate relevant locks and synchronize baseline pins through existing review.

Build wheel and sdist with existing `make build`/`make check` (internal commands may
change). Inspect version, Requires-Python, Requires-Dist, intended extras, exports,
py.typed and contents. Install the wheel into clean supported Python environments
outside the source checkout; verify import path and representative existing public
behavior without editable paths or Node. Build/install from the sdist in an isolated
directory and verify no missing generated/input files or uncontrolled owned build
inputs. Retain native dependency install proof; Dataplane separately proves Alpine.

### 6. Documentation, release decision and consumer handoff

Update affected README, deployment/setup instructions and stale support statements
in repository guidance. Explain `venv`, selected-interpreter setup, lock regeneration
and Node's development-only role. Do not add a new knowledgebase article for an
unchanged product workflow. Record any distribution/support change in the changelog.

Classify the outcome: existing artifact sufficient; repository tooling-only change;
or changed distribution/support contract requiring a release. Inspect real artifact
availability and history; a tag/source version is not publication. If a new release
is required, record it as a user-owned follow-up after plan execution. Do not run
`/repair-release`, `/push-release-branch` or `/push-github` under this plan.
Their existing sequence and approval boundaries remain available for the user's
subsequent release. No release version bump is required to complete this plan.

Retain version mirrors, token authentication, existing-version handling, distribution
checks and publication verification. Command/CI internals may change, including
necessary required checks; coverage and human release authority remain. Do not
invent a version, move tags or force a release when the existing artifact suffices.

Handoff to Dataplane records source revision, supported-runtime results, local
wheel/sdist identity/results, canonical checker revision/parity and required consumer
action. SDK completion requires this evidence, not publication. If a changed artifact
is needed, mark registry availability as an external user-owned follow-up. A local
package is not an available registry release. Dataplane owns its own pin/locks and
full application integration gate; final registry-based consumption waits for the
user's publication.

Necessary publishing-workflow changes remain in scope, verified without uploading,
creating releases or dispatching publication. Preserve their guards for later use.
