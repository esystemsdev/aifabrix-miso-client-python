### 2. Lock owned environments and retain venv workflows

Keep pyproject.toml as effective consumer metadata and setup.py as its compatibility
mirror. Preserve existing requirements.txt/requirements-test.txt as range-based
inputs where currently used; do not silently repurpose sdist range files as locks.
Use an owned requirements/ directory for runtime.in, dev.in and build.in plus
runtime.lock, dev.lock and build.lock hashed outputs. Runtime input reuses existing
runtime requirements; dev includes runtime/test inputs plus actual gate tooling;
build lists controlled build tools. Document generation/install commands once in
existing Make guidance. Add suffix variants only when interpreter/platform evidence
requires them, not one speculative matrix of locks. Consumer metadata stays ranges.


Use pip-tools to generate hashed third-party runtime/test/development/build
environments from reviewed inputs. Keep package dependency ranges in metadata;
include all tools actually used by Make/CI: pytest plugins, black/isort, ruff,
basedpyright, mypy, build, twine, setuptools/wheel and controlled bootstrap/generator
requirements. Constraints alone do not install runtime dependencies.

Prefer one compatible marker-aware resolved set where it serves all supported
interpreters. If resolution/platform differences require separate locks, use only
the necessary explicit environment variants with deterministic generation commands.
Pin generator/interpreter assumptions and check regeneration in CI without an
implicit upgrade mode. Install third-party dependencies with `--require-hashes`;
wrong/missing hashes fail. Do not add a network-dependent offline validation gate.

Install editable local SDK source separately without re-resolving dependencies.
Control PEP 517 build dependencies explicitly; hashing an sdist does not control
its build-isolation downloads. Use the existing backend with controlled build
requirements and an appropriate no-isolation invocation when needed. Verify
consumer sdist installation still works normally without repository Node tooling.

Extend existing Make setup rather than inventing another installer. Retain `venv`;
allow explicit interpreter selection and verify the environment interpreter before
reuse. Safely recreate only the managed incompatible environment, preserving .env
and unrelated files. Use runtime/lock identity for cache invalidation; failed
installation must not leave success state. Preserve editable `install`/`install-dev`
interfaces while routing owned development setup through controlled dependencies.

Additional implementation best-practices to apply:

- Hash controlled third-party inputs and keep consumer dependency ranges separate.
- Recreate only the managed incompatible environment and retain explicit interpreter selection.
