# 52.0 Client token mint failure coalescing

## Overview

A reused legacy/local SDK client serializes concurrent failed token mints but
retries once per waiting caller. Reproduction: 24 concurrent callers produce 24
failed HTTP requests. Successful mint reuse and managed bootstrap refresh already
work. The user authorized this repair on 2026-09-29 after recommendation-only review.

## Scope and contract

- One shared in-flight mint per `ClientTokenManager` on its owning event loop;
  all callers awaiting that attempt receive its token or typed failure.
- Failure is not cached. The next call after an attempt finishes can retry
  immediately. No new cooldown, retry loop, Redis dependency or cross-client cache.
- Cancelling a waiter does not cancel shared work. If all waiters leave, consume
  eventual exceptions; client close cancels and awaits any outstanding mint.
- Clearing a token invalidates pending mint results. A late result cannot restore
  the token or be returned to existing waiters; a subsequent call can retry after
  the invalidated attempt settles. Preserve managed runtime guards and deadlines.
- Recheck token validity using current time after acquiring the existing lock.
- Preserve existing error/status/correlation handling and successful token expiry.
- Separate clients keep separate state. Credential/configuration changes require
  appropriate client lifecycle management; this change introduces no shared identity cache.

Out of scope: optional Redis bootstrap configuration, changing expiry fallback,
consumer factory reuse, rejected pipeline credentials, encryption-key configuration,
release publication/version bump, and deployed service changes. Those incident
causes remain separate; SDK request coalescing does not repair invalid credentials.

## Validation correction

At repository commit `bd355ba` (package version `5.0.2`), the proposed causal chain
below is not supported by source:

- `AuthService.get_environment_token()` delegates through `HttpClient` and
  `InternalHttpClient` to `ClientTokenManager.get_client_token()`; Redis is not
  consulted on this path.
- In local mode, `init_secrets()` calls `load_config()`, including its optional
  `REDIS_HOST` configuration. The token manager already holds a token in memory,
  applies a 30-second refresh buffer, and uses a double-checked async lock.
- In client-credentials mode, the manager delegates to `SecretsRuntime.get_token()`.
  That runtime already owns snapshot tokens, coalesces refreshes, shields shared
  work from waiter cancellation, and enforces invalidation and failure cooldown.
  Missing Redis configuration does not disable this lifecycle.
- Bootstrap snapshots require a 300-second token deadline, a 120-second refresh
  schedule, and a separate 900-second secret deadline (`bootstrap_snapshot.py`).
  The reported 900-second JWT lifetime must be tied to the deployed mode/version;
  it cannot replace the bootstrap contract.

The following incident narrative is retained as reported evidence, not verified
root cause. The initial plan review did not access dev03. The follow-up investigation below
inspected deployed code, the consumer evidence file and controller logs; it
supersedes the original rate-limit attribution.

## Deployed reproduction and diagnosis

Investigated 2026-09-28 using read-only Docker inspection and isolated Python
processes with mocked HTTP. No real mint/decrypt calls, worker restarts, runtime
configuration changes or product-code edits were made.

### Deployed version, mode and ownership

- Dev03 API, worker and beat containers all report installed `miso-client==5.0.2`,
  `MISO_AUTH_MODE=client-credentials`, `REDIS_URL` present and `REDIS_HOST` absent.
  The worker imports `/usr/local/lib/python3.11/site-packages/miso_client/`.
- SHA-256 matches local source for bootstrap, bootstrap runtime/transport, client
  token manager, internal HTTP client and auth service (six files).
- Dataplane `app/core/secret_runtime.py` retains one runtime per process; ordinary
  `getMisoClient()` returns `runtime.client`. Prefork children have separate owners.
- Deployed `app/core/auth_miso_client.py:253` creates a new `MisoClient` for each
  explicit credential pair that differs from default settings. Its caller,
  `ControllerApiClient.get_client_token()`, initializes that new client per call.
  A missing Redis configuration does not explain the managed-runtime behavior.

### Public API reproduction

The same script exercised `init_secrets()` → `runtime.client.get_environment_token()`
on the local checkout and inside the dev03 worker container. Both produced
identical results with 24 calls per scenario:

| Scenario | Token mints | Bootstrap calls | Result |
| --- | ---: | ---: | --- |
| Local, reused runtime, sequential | 1 | 0 | 24 successes |
| Local, reused runtime, concurrent | 1 | 0 | 24 successes |
| Managed, reused runtime, sequential | 1 | 1 | 24 successes; both HTTP calls occurred at startup |
| Managed, reused runtime, concurrent | 1 | 1 | 24 successes; no per-call mint |
| Local, new runtime per call | 24 | 0 | 24 successes |
| Managed, new runtime per call | 24 | 24 | 24 successes |
| Local, reused runtime, concurrent synthetic mint 401 | 24 | 0 | 24 failures; lock serializes failures but does not share them |

A separate harness executed the actual deployed credential-factory function AST
with synthetic settings, the real installed SDK, and mocked HTTP. The config
builder/default-client accessor were fixture substitutions to avoid booting the
whole application: default credentials yielded **1 client / 1 mint**; explicit
non-default credentials yielded **24 clients / 24 mints**. This proves the factory
mechanism, not attribution of every production request to a particular call site.

### Controller evidence

A bounded capture of controller logs contains these operation-error records
(counting the operation error once, excluding duplicate “Request rejected” logs):

- **120 token 401s: `Pipeline credentials inactive`.** Their recorded caller IDs
  do not match the worker's default application identity (compared internally;
  raw identifiers and credentials are omitted from the saved report).
- **298 token 401s: `Invalid credentials`**, likewise for non-default identities
  in this capture. These counts describe the captured window, not all history.
- **101 decrypt 401s: `Invalid encryption key`.** These are controller decryption
  validation errors, not evidence that token acquisition failed first.
- Controller startup explicitly logs **`Rate limiting disabled`**. The observed
  token failures have credential-denial reasons, not a demonstrated rate refusal.

Source corroboration: Miso's `pipeline-auth-core.helper.ts` returns “Pipeline
credentials inactive” when no active pipeline configuration is available;
`SecurityParameterService.validateEncryptionKey()` raises “Invalid encryption key”.
The older consumer evidence file was also inspected inside `/app`; its inference
that decryption 401s necessarily indicate token failure is superseded by these
controller-side reasons.

### Decision and evidence artifacts

The original managed-runtime cache diagnosis is disproved for the tested installed
SDK. Do not implement another token hold or promise it will resolve this incident.
Re-scope before coding:

1. Dataplane: review ownership/cleanup of explicit-credential clients and reuse by
   identity; this is client lifecycle management, not a second token cache.
2. Controller/application configuration: resolve the rejected non-default
   credentials and pipeline activation. Reuse cannot make invalid credentials valid.
3. Decryption configuration: trace why the failing worker sends a key the
   controller rejects. No key values were inspected or changed in this review.
4. SDK, separately: the local/legacy failure burst is reproduced; consider a
   bounded shared failure/cooldown contract. Managed mode already has cooldown.
   This issue does not establish the cause of the observed decryption denials.
