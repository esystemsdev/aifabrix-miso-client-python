# 53.0 Browser-session cookie refresh for server-side consumers

## Problem

dev01, 2026-10-15 09:22 UTC: the user opened
`https://dev01.aifabrix.dev/data/api/v1/rest/ra-sales-representative/docs` directly and got
401 "User session is invalid or expired"; the same for `/api/v1/mcp/.../docs`.

| Step | Evidence |
| --- | --- |
| Cookie token issued | `iat` 09:16:55, `exp` 09:21:55 (Keycloak access token, 5 min) |
| Requests | 09:22:02 and 09:22:35, same `jti` — the cookie was never renewed |
| Miso | `POST /api/v1/auth/validate` → `ERR_JWT_EXPIRED` |
| SDK (Dataplane) | `miso_client.utils.user_token_refresh`: "No refresh mechanism available for user …" |
| Dataplane UI | refreshes only after its own GET returns 401 (`fetchReplayableProtectedRequest` → recover → replay); no proactive timer, and a top-level link has no UI code at all |

The session itself was alive: Miso keeps the encrypted refresh token in its browser-session
store (30 min rolling TTL) and renews on bodyless `POST /api/v1/auth/refresh`
(`auth-core-session.routes.helper.ts`, `setAuthBrowserSession` → new `miso_access_token`
cookie, path `/`). Nobody on the server side calls it.

## Why miso-client-python

Auth and transport behaviour belongs in the SDK, not in each consumer (Dataplane rule:
SDK fixes belong in miso-client). The SDK already owns user-token validation and has a
refresh registry (`UserTokenRefreshManager`) that can never work for cookie sessions,
because the refresh token never leaves Miso. The canonical, bodyless session refresh from
plan 45.1 is the right path; this plan adds the server-side caller for it.

## Design

1. **Input:** the token came from the `miso_access_token` cookie (the consumer says so;
   Bearer-header tokens are never refreshed — device and M2M flows stay separate, 45.1).
2. **Expired?** Local `exp` check first (`token_utils` / `jwt_tools`); if not locally
   expired, validate with Miso as today. Refresh only on expiry — a bad signature, a
   revoked session or a wrong issuer stays a 401.
3. **Refresh:** `POST {controller}/api/v1/auth/refresh`, no body, header
   `Cookie: miso_access_token=<expired>`. Read the new token from the response
   `Set-Cookie` and `data.expiresIn`. Miso answers "no active browser session" when the
   30-minute session has ended → 401 as today (user logs in again).
4. **Once per expired token:** `shared_task` single-flight keyed by SHA-256 of the expired
   token. Miso deletes the previous session on rotation (`putBrowserSessionRecord` with
   `previousAccessToken`), so a memo old→new (until the new `exp`) answers later requests
   that still carry the old cookie.
5. **Result:** `SessionCookieValidation(token, user, set_cookie)`. The consumer validates
   with the new token, serves the request, and sets the returned cookie on the response,
   so the browser holds the renewed cookie.

## Dependencies and risks

- **Miso contract (verify first):** server-forwarded cookie accepted on `/auth/refresh`;
  rate limiter `authRefreshSessionLimiter` must tolerate one refresh per 5 minutes per
  session from the consumer's IP. If either fails, the fix moves to a Miso plan first.
- **Multiple replicas:** two replicas refreshing the same cookie at once — the second
  fails and that one request is 401 (UI recovers; a direct link can be reloaded). A Miso
  grace window for `previousAccessToken` would close it; out of scope here, noted for Miso.
- **Concurrent browser refresh:** the UI may refresh while a server refresh is in flight;
  the response that sets the cookie last wins. Covered by the memo for requests in the
  same process.

## Miso contract (recorded 2026-10-15)

Verified from the Miso controller source (`aifabrix-miso` 2.1.20, `routes/auth-core-session.routes.helper.ts`,
`auth-browser-session.helpers.ts`) and its integration tests (`auth-core.routes.test.ts`); live dev01 proof is part of `manual-proof`.

- Request: `POST /api/v1/auth/refresh`, no body, `Cookie: miso_access_token=<access token>`. Miso reads only the cookie;
  the session record is keyed by the access token, so an expired token is accepted. `x-client-token` is not required
  (tests call without it); the SDK sends it anyway.
- Success: 200, body `{"data": {"authenticated": true, "expiresIn": <s>}}`, header
  `Set-Cookie: miso_access_token=<new>; Path=/; HttpOnly; SameSite=Lax` (+ `Secure` in production).
- No session: 401 `{"type": "/Errors/Unauthorized", "detail": "No active browser session"}`.
- Rotation: `putBrowserSessionRecord(new, ..., previousAccessToken)` deletes the old record (memo is required).
- Rate limit: `authRefreshSessionLimiter` is 20 per 15 min **per caller IP**; deploy default `DISABLE_RATE_LIMIT=true`.
  With rate limiting on, all users of one consumer share 20 refreshes per 15 min — Miso follow-up before enabling it.

## Implementation notes

- Entry point lives in `SessionCookieMixin` (`services/browser_session_refresh.py`); `MisoClient` inherits it, so
  `client.py` stays at 499 lines.
- The refresh uses a short-lived `httpx.AsyncClient`: the shared SDK client's cookie jar would otherwise store the
  renewed `miso_access_token` and replay it on later controller calls.
- Expiry trigger is the local `exp` with a 30 s leeway (`AuthService.get_user` swallows Miso error codes). This also keeps
  the auth validation cache (TTL `exp - 30s`) from answering for an expired token.
- `http_log_masker` needed no change: `DataMasker` masks any header containing `cookie`; covered by a test.
- The refresh call is not in the SDK HTTP audit log (like `/api/auth/token`); Miso audits refresh server-side.

### Recommendations

- **Error visibility (design gap):** `AuthService.validate_token`/`get_user` catch all errors and
  return `False`/`None`, so "Miso `ERR_JWT_EXPIRED`" in Design step 2 cannot be read through
  them. Rely on the local `exp` check as the primary trigger, and add a narrow typed path
  (in the new module, not `auth.py` at 491/500) only if the contract proof shows clock-skew cases.
- **Response headers (design gap):** `HttpClient.post` and `AuthApi.refresh_session_token`

  raw-response call that still goes through the client-token interceptor and audit masking.
- **Auth cache:** make sure a cached validation of the old token (TTL `exp - 30s`) cannot
  answer for it after expiry, and that the new token's validation is cached normally.
- **Prior decision:** CHANGELOG 4.19.1 states browser orchestration is out of scope for Python;
  the CHANGELOG entry should state that this is server-side refresh only.
- **Rate limit / replicas:** keep the `authRefreshSessionLimiter` and multi-replica notes as
