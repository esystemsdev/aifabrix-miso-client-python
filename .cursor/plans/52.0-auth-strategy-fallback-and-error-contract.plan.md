# 52.0 Auth-strategy fallback, and preserving the controller's answer

## Defect 1 — the fallback never runs

`AuthStrategyHandler.get_default_strategy()` returns
`methods=["bearer", "client-token"]` (`utils/auth_strategy.py:73`), and
`_try_auth_methods` is written to try each in turn, treating a 401 as "continue
to the next method" (`utils/internal_http_auth_strategy.py:85-99`):

```python
for auth_method in auth_strategy.methods:
    try:
        result = await self._request_with_single_auth_method(...)
        return True, result, None
    except httpx.HTTPStatusError as error:          # <- never matches
        should_continue = self._handle_auth_method_http_error(error, auth_method)
        ...
    except ValueError as error:
        ...
```

But the transport beneath it converts that exception before the handler sees it
(`utils/internal_http_client.py:290-296`):

```python
except httpx.HTTPStatusError as e:
    failure = self._create_error_from_http_status(...)   # -> MisoClientError
except httpx.RequestError as e:
    failure = self._connection_error(e, controller)
raise failure
```

`MisoClientError` is neither `httpx.HTTPStatusError` nor `ValueError`, so the
`except` clauses do not match, the exception propagates straight out of the loop,
and **only the first method is ever attempted**.

Observed stack, from a dataplane worker:

```
internal_http_auth_strategy.py:87  in _try_auth_methods
internal_http_auth_strategy.py:144 in _request_with_single_auth_method
internal_http_client.py:373        in request
internal_http_client.py:270        in post
internal_http_client.py:296        in _execute_body_request
    raise failure
miso_client.errors.MisoClientError: Managed runtime request failed
```

Escaping *from* line 87 is the proof: had a handler matched, the loop would have
continued to `client-token` instead.

### Why it matters

`POST /miso/api/security/parameters/{encrypt,decrypt}` accepts **`x-client-token`
only** — `packages/miso-controller/src/routes/security/parameters.routes.ts:5`,
both routes behind `requireClientToken`. Asked directly, the controller is
explicit:

```
Authorization: Bearer <token>   -> 401 {"code":"bootstrap_token_invalid",
                                        "detail":"x-client-token header is required"}
x-client-token: <same token>    -> 422  (validation only: auth passed)
```

So the client holds a usable credential, the endpoint states which form it needs,
and the fallback designed to switch forms never executes. Confirmed from inside a
running worker: `clientTokenMinted: true` and `encryptionKeyOnClient: true`, and
the encryption call is still refused.

## Defect 2 — the controller's answer is deleted in transit

`services/encryption.py:191-205`:

```python
correlation_id = extract_correlation_id_from_error(error)   # logged, then lost
logger.error(..., extra={"correlationId": correlation_id})
raise EncryptionError(
    str(error),                      # summary only
    code="ENCRYPTION_FAILED",        # overwrites the controller's code
    parameter_name=parameter_name,
    status_code=error.status_code,
) from error
```

`MisoClientError` carries `error_body` (already secret-masked), `error_response`
(RFC 7807) and `auth_method` (`errors.py:25-55`). None are passed on.
`_raise_decrypt_error` (`:207`) does the same.

Measured from a consumer catching the result:

| Field | Controller sent | Survived to the consumer |
| --- | --- | --- |
| `status_code` | 401 | **yes** |
| `code` | `bootstrap_token_invalid` | no — replaced by `ENCRYPTION_FAILED` |
| `detail` | "x-client-token header is required" | no |
| `auth_method` | bearer | no |
| correlationId | present | no — logged inside the SDK only |

`auth_method` is the single field that names this failure outright. Dropping it
is what turned a precise refusal into "Managed runtime request failed", which the
consumer then surfaced four layers later as OpenAI reporting an invalid API key
and HubSpot reporting none at all. That cost about a day to attribute.

## Why the suite is green while both defects are present

Asked directly — the tests pass, so how is this broken? Because no test
exercises the failing path, and two tests assert the defect as intended
behaviour. Any fix must repair these first or it will present as a regression.

### The fallback test mocks the exception production never raises

`tests/unit/test_auth_strategy.py:140`:

```python
error_401 = httpx.HTTPStatusError("401 Unauthorized", ...)
with patch.object(http_client, "request", new_callable=AsyncMock) as mock_request:
    mock_request.side_effect = [error_401, {"data": "success"}]
```

`request` is the method that performs the conversion: in production it reaches
`_execute_body_request`, which turns `httpx.HTTPStatusError` into
`MisoClientError` before the strategy loop sees anything. Patching `request`
replaces that conversion with a correct one, then asserts the handler catches
what the mock handed it.

The test therefore proves "given an `httpx.HTTPStatusError`, the fallback
works" and never asks whether such an exception can arrive. It cannot. The mock
is placed exactly on the seam where the defect lives.

It also uses `methods=["bearer", "api-key"]` rather than the
`["bearer", "client-token"]` default that the affected callers run.

### The encryption test asserts the deleted contract

`tests/unit/test_encryption_service.py:186-197`:

```python
mock_http_client.post.side_effect = MisoClientError("Internal server error", status_code=500)
...
assert exc_info.value.code == "ENCRYPTION_FAILED"
```

This is defect 2 recorded as expected behaviour — preserving the controller's
`bootstrap_token_invalid` turns this test red. The injected error is also
constructed without `error_body`, `error_response` or `auth_method`, so even a
corrected implementation would have nothing to observe here.

### No live test reaches the endpoint that fails

`tests/manual/` holds two live cases, both bootstrap and configuration read
(`init_secrets`, `secrets.require`, `refresh`, `close`). Neither calls
`encryption.encrypt` or `decrypt`, so `POST /miso/api/security/parameters/*` —
the only routes behind `requireClientToken`, and the only ones that refuse a
Bearer token — are never exercised. `tests/manual/test_config_loader_encryption_key.py`
is named for encryption but only asserts `ENCRYPTION_KEY` /
`MISO_ENCRYPTION_KEY` precedence; no call is made.

`test_live_invalid_credentials_are_terminal` does assert a failure, but on the
normalized `BootstrapError.code == "authorization-denied"`. It would still pass
with every controller diagnostic stripped.

### The structural reason

The defect is observable only when the **first** auth method is refused with a
401. Bootstrap succeeds on bearer, so the loop returns on its first iteration
and the unreachable `except` clauses are never entered in a passing run. A suite
that never produces a real 401 at that layer cannot detect a broken 401 handler.

## Status against 5.0.3 (checked 2026-09-29)

5.0.3 does **not** address either defect. Diffed 5.0.2 and 5.0.3 wheels from the
index; exactly three files differ:

| File | Change in 5.0.3 |
| --- | --- |
| `utils/client_token_manager.py` | concurrent mints coalesced onto one shared task; `_generation` counter invalidates in-flight results; new `close()` |
| `utils/internal_http_client.py` | `close()` now awaits `token_manager.close()` |
| `__init__.py` | version string |

`services/encryption.py` and `utils/internal_http_auth_strategy.py` are
byte-identical between the two releases. Both defect sites were re-read in the
5.0.3 wheel and are unchanged: `_raise_encrypt_error` still overwrites `code`
with `ENCRYPTION_FAILED` and drops `error_body` / `error_response` /
`auth_method`, and `_try_auth_methods` still catches only
`httpx.HTTPStatusError` while `_execute_body_request` still raises
`MisoClientError`.

The mint coalescing is a real fix for a real concurrency hazard, and it is not
this one — note that it is also not the token-lifecycle-caching theory recorded
under *Out of scope*, which remains disproven.

### 5.0.3 raises the cost of defect 2

Miso has extended the controller's RFC 7807 answer to identify the attempted
auth method and, where it can do so without letting a caller enumerate clients,
the verified client identity. Consumers were asked to preserve `status`,
`detail`, `code`, `authMethod`, `clientIdentity`, `instance` and
`correlationId` rather than replace them with a generic message.

On the Python encryption path they cannot: `_raise_encrypt_error` deletes
`error_body` and `error_response` before any consumer sees them. `authMethod`
is precisely the field that names defect 1 in one line, and it is the field the
SDK discards. Until `preserve-error-contract` lands, the controller-side
diagnostics work does not reach a Python consumer at all.

Verified consumer-side: `aifabrix-dataplane`'s `app/core/miso_error_detail.py`
already reports every one of those fields when they are present, and omits
`clientIdentity` rather than inventing it when the controller withholds it.
The gap is the SDK layer between them.

## Scope

### In scope

- Making the fallback recognise the failure type the transport actually raises.
- Carrying `error_body`, `error_response`, `auth_method` and the correlation id
  through the encryption wrapper, and not overwriting the controller's `code`.

### Out of scope

- miso-controller behaviour. The endpoint's requirement and its refusal are
  correct, and `aifabrix-miso` plan 261.0 covers naming the client on 401s.
- Token lifecycle caching. An earlier revision of this plan blamed a missing
  runtime cache; measurement disproved it — a reused runtime serves 24 calls
  from 1 mint without Redis. That diagnosis was wrong and is recorded here so it
  is not repeated.
- Any consumer-side workaround.

## Acceptance

- A request whose first auth method is refused with 401 proceeds to the next
  method in `AuthStrategy.methods`, and succeeds where that method is accepted.
- An endpoint accepting only `x-client-token` is reached successfully with the
  default `["bearer", "client-token"]` strategy.
- A raised `EncryptionError` still carries the controller's `code`, `detail`,
  `auth_method` and correlation id; `ENCRYPTION_FAILED` no longer masks a more
  specific code.
- No secret value is added to any error surface — `error_body` is already masked
  by the SDK and must stay that way.

## Reporting consumer

`aifabrix-dataplane`. Its `tests/manual/test_controller_auth.js` asserts token,
encrypt, decrypt, round trip and stored-secret resolution separately for the API
process and the lifecycle worker, and reports this failure class in about
30 seconds; useful as an independent check on a fix. Field evidence is recorded
in `aifabrix-miso/.cursor/plans/261.0-auth-failure-diagnostics-name-client-and-permission.plan.md`.

### Implementation

- Auth strategy catches the SDK error produced by the real transport, preserves
  the final error payload, and obtains the current client token for each client
  auth attempt. Ordinary 401s advance to the next configured method; non-401s,
  connection failures and bootstrap identity/expiry codes do not replay requests.
- HTTP diagnostics are sanitized before exception construction. Managed mode
  retains only diagnostic fields. Existing DataMasker handles sensitive keys;
  known credential values (including bearer/application tokens, encryption keys,
  and encryption payload values) are also removed from diagnostic strings.
  Raw JSON does not reappear through a fallback exception message.
- RFC 7807 and legacy structured errors retain code, detail, auth method,
  controller-disclosed identity, instance and correlation (body or header).
  HTTP status remains authoritative over a conflicting status in the payload.
- Encryption wrappers pass through sanitized payloads and structured errors and
  prefer the controller's specific code. Code-less errors retain existing fallback
  codes. Exceptions expose `correlation_id` for consumer diagnostics.
- No package version change, publication, credential rotation, controller change,
  or consumer deployment was performed. Credentials were passed only in process
  memory. The repository `.env` was not modified.
