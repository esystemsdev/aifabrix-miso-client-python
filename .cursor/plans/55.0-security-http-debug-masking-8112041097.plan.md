# Python SDK: fix secret leakage in HTTP logs

## Outcome and scope

**Implement the fix and add regression tests.** Inspect current behavior first, fix every confirmed gap in the contract below, and retain tests for protection already present. A report or tests alone do not complete this plan while a leak remains. The same requirement applies to the companion SDK plan.

Keep the change inside this SDK: existing masking defaults, HTTP log construction, focused tests and a short documentation update. Reuse existing helpers. No new logging framework, configuration switch, dependencies, public API, endpoint wrapper or broad refactor. Do not modify consumer repositories.

The separate TypeScript `createErrorResponse` error-type issue is outside this logging plan and remains unresolved by it.

## Current evidence

Local metadata reports Python SDK **5.2.2**; the original issue report identifies a consumer on 5.2.1. `miso_client/utils/sensitive_fields_config.json` already contains `encryptionKey` and `secret`; existing substring matching covers `clientSecret`. `plaintext` and `value` are missing. The fallback set in `data_masker.py` also lacks `encryptionkey`.

`http_client_logging_helpers.py` delegates to `http_client_logging.py`; `_prepare_debug_context` masks request/response bodies without excluding `/api/security/`. Inspect the existing `http_log_masker.py` and formatter only as needed to apply the guard and verify the output. These are source observations, not executed regression results.

## Minimal implementation

1. **Complete existing defaults.** Add missing `plaintext`, `encryptionkey` and `value` protection to packaged defaults and hardcoded fallback sets as needed. Verify that `secret` and `clientSecret` remain masked. Use existing case-insensitive normalization and recursive masking; do not add redundant aliases or rewrite the matcher. Preserve existing custom configuration semantics and document the intended additional masking of `value`.
2. **Exclude security bodies at log construction.** For `/api/security/` requests, omit both request and response bodies (or use a constant placeholder) before passing data into log formatting. Response omission closes the decrypt leak. Use a small shared predicate only where multiple existing paths need it; avoid a new policy abstraction. Reuse current URL parsing/resolution for relative and absolute URLs and supported base paths. Check the pathname boundary, not a substring anywhere in the URL.
3. **Keep error logs safe.** Apply the same rule on failures. On security calls, do not log raw exception messages or response/config dumps that can echo secrets; use a fixed generic message plus safe status/code/correlation metadata. This includes both minimal and standard audit paths in `http_client_logging.py` and the existing `logger.error(..., exc_info=error)` calls in `EncryptionService`. Omit `exc_info`, raw exception text and parameter names from these secret-bearing diagnostics while preserving the existing caller-visible error contract. Do not redesign error objects.
4. **Preserve useful behavior.** Retain safe audit metadata, existing header masking and ordinary nonsecurity logging. Do not disable all audit events. Do not mutate outgoing payloads or the plaintext returned to the caller. Body exclusion is unconditional for security routes, including when custom field masking is permissive, and applies to all existing paths/levels that emit bodies.

## Focused regression tests

Use existing test fixtures, synthetic markers and mocked external I/O. Keep the real masker and production HTTP logging code running. Capture the final logger records (messages and complete context); inspect the existing console/output sink as well if it has a distinct formatting path. Await asynchronous logging before asserting. Assert a safe event exists so that disabling logging cannot make the test pass.

Use parameterized cases rather than a Cartesian product of every route, level, configuration and response type:

| Test group | Required assertions |
| --- | --- |
| Masking defaults | `plaintext`, `encryptionKey`, `value`, `secret`, `clientSecret` and mixed-case variants are masked; one nested object/array case; input unchanged. Exercise the existing hardcoded fallback once and reuse loader tests for malformed/missing files. |
| Debug encrypt/decrypt/delete | Run all three HTTP calls through the existing client with debug enabled. Markers in request bodies and the decrypt response never appear anywhere in captured logs. Include a marker under an innocuous field to prove bodies are omitted, not merely masked. Verify outbound payload and decrypt result stay intact. |
| Failure path | One representative security HTTP error that echoes a marker in its body/message produces safe audit/debug logs and retains status/correlation metadata. Cover minimal and standard audit without duplicating the transport setup. Use `caplog` once for the distinct `EncryptionService` stdlib failure sink and scan its complete formatted exception output. Add another failure test only if code inspection finds another distinct body-emitting path. |
| Route guard and control | Small table for relative URL, absolute URL with query, and a supported base-path form when used by the SDK. `/api/security-other/` and security text only in a query must not match. One normal request still logs permitted masked diagnostics. |
| Other emitting paths | Cover each distinct existing body-emitting formatter/audit path once, using its most verbose level; use parameterization if level-specific branches exist. One permissive masking configuration proves the security body guard cannot be bypassed. |

Record a failing baseline for the reproduced defect and a passing result after fixing it. Already-safe cases still get regression coverage; do not manufacture failures. No live secrets, external services, exhaustive URL fuzzing or new test framework are required.

Extend `tests/unit/test_data_masker.py` and the existing HTTP logging tests. Keep transport-level cases together in `tests/unit/test_security_http_logging.py` (new) if that is clearer than extending an existing module. Reuse HTTPX MockTransport patterns from `test_auth_encryption_transport_contract.py`, and the existing task-completion helper. Use the generic client method for delete if no dedicated SDK method exists; adding one is outside scope.
